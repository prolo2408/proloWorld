Grundidee

Wozu Git gut ist

Git beantwortet drei Fragen.

Was habe ich geändert? Was lief vorher? Wie komme ich dahin zurück?

Ohne Git ist die Antwort auf die dritte Frage eine Kopie mit dem Namen index-alt-final-2.html. Mit Git ist sie ein Befehl.

Für den Stack kommt ein vierter Zweck dazu: Git ist der Weg vom Arbeitsrechner auf den Server. Was unter /opt/stack liegt, ist eine Kopie des Repositorys — und wird über Git aktuell gehalten, nicht über Datei-Kopieren.

Der Unterschied zu GitHub Git ist das Programm auf dem Rechner. GitHub ist nur ein Ort im Netz, an dem eine Kopie liegt. Git funktioniert ohne GitHub; GitHub ist praktisch, weil mehrere Rechner dieselbe Kopie erreichen — dein Arbeitsrechner und der Server.
Das Modell, auf das es ankommt

Die vier Orte

Fast jedes Missverständnis mit Git kommt daher, dass man diese vier Orte verwechselt.

1
Arbeitsverzeichnis Die Dateien, die du bearbeitest. Was du im Editor siehst.
↓ git add
2
Bereitstellung Ein Vorraum. Hier sammelst du, was in den nächsten Commit soll. Man kann drei von fünf geänderten Dateien bereitstellen und die anderen zwei später.
↓ git commit
3
Lokales Repository Die Historie auf deinem Rechner. Ab hier ist die Änderung festgehalten und wiederauffindbar — aber nur bei dir.
↓ git push  ·  ↑ git pull
4
GitHub Die Kopie im Netz, in Befehlen origin genannt. Von hier holt der Server.
Die zwei Sätze, die alles erklären Wer committet hat, hat noch nicht gepusht — die Änderung liegt nur auf seinem Rechner.
Wer auf GitHub etwas sieht, hat es noch nicht auf dem Server — dort muss erst geholt werden.
Fünf Befehle

Der Alltag

Damit deckst du neunzig Prozent ab.

Wo stehe ich?

git status

Der wichtigste Befehl. Er sagt, auf welchem Zweig du bist, welche Dateien geändert sind, was bereitgestellt ist und ob du gegenüber origin vor- oder hinterherhängst. Vor jedem anderen Schritt einmal lesen.

Änderung festhalten

git add .
git commit -m "Kurz, was und warum"
git push

add . stellt alles Geänderte bereit. commit hält es fest. push lädt es zu GitHub.

Die Nachricht nach -m liest du selbst in einem halben Jahr wieder. „Änderungen" hilft dir dann nicht; „Bordbuch: Seitenleiste statt Reiterzeile" schon.

Neuen Stand holen

git pull origin main

Holt, was auf GitHub in main steht, und schreibt es in dein Arbeitsverzeichnis. Das ist der Befehl, der auf dem Server laufen muss, bevor du aktualisierst.

Was hat sich geändert?

git diff              # noch nicht bereitgestellt
git diff --staged     # bereitgestellt, noch nicht committet
git log --oneline -10 # die letzten zehn Commits
Nebenspuren

Zweige und Pull Requests

Ein Zweig ist eine Nebenspur, auf der man arbeiten kann, ohne den Hauptstand anzufassen.

Der Hauptstand heisst main. Er soll immer lauffähig sein — von dort holt der Server. Wer direkt auf main arbeitet, hat jeden Halbfertigstand sofort dort stehen.

Darum: Arbeit passiert auf einem eigenen Zweig.

git checkout -b mein-zweig   # neuen Zweig anlegen und hinwechseln
git checkout main            # zurück auf den Hauptstand
git branch                   # welche Zweige gibt es, wo bin ich?

Der Pull Request

Ein Pull Request ist die Bitte: „Nimm meine Nebenspur in main auf." Er wird auf GitHub angelegt, zeigt genau die Unterschiede, und man kann ihn durchlesen, bevor man ihn annimmt.

Das Annehmen heisst mergen (zusammenführen). Erst danach steht die Änderung auf main.

Der Fehler, der dreimal passiert ist Ein gepushter Zweig ist nicht auf main. Solange der Pull Request nicht gemergt ist, holt git pull origin main nichts davon — und meldet Already up to date. Das ist keine Fehlermeldung, sondern die Wahrheit: auf main gab es wirklich nichts Neues.
Der Weg nach draussen

Vom Zweig auf den Server

Zwischen „gepusht" und „läuft" liegen drei Schritte. Fehlt einer, meldet alles Erfolg und nichts ändert sich.

SchrittWoWas
1. MergenGitHub Pull Request annehmen. Erst danach steht es auf main.
2. HolenServer cd /opt/stack && git pull origin main
3. AktualisierenServer sudo prolo aktualisieren

Zwei Meldungen, die man kennen muss

Already up to date. — der Pull hat nichts geholt. Entweder ist wirklich nichts Neues da, oder es liegt auf einem Zweig, der noch nicht gemergt wurde.

CACHED [3/5] COPY server.py index.html — beim Bauen war die Datei byte-identisch zum letzten Mal. Es wurde die alte Fassung neu gebaut. Fast immer heisst das: Schritt 2 fehlt.

Dagegen gibt es jetzt eine Wache prolo aktualisieren prüft vor dem Bauen, ob der Stand unter /opt/stack hinter origin liegt, und bricht mit dem nötigen Befehl ab, statt eine alte Fassung neu zu bauen und Erfolg zu melden.
Fallgruben

Was schiefgeht, und woran man es erkennt

Ein Geheimnis ist mitgegangen

Das ist der einzige Fehler, der nicht zurückzunehmen ist. Einmal gepusht, muss man davon ausgehen, dass es draussen ist — Zurücknehmen des Commits genügt nicht, die Historie enthält es weiter.

Der einzig verlässliche Weg: das Geheimnis selbst ändern. Passwort neu setzen, Schlüssel neu erzeugen, Token widerrufen.

Verhindert wird das über .gitignore — eine Liste von Mustern, die Git ignoriert. Aber Achtung:

.gitignore wirkt nicht auf bereits verfolgte Dateien Was schon einmal committet wurde, bleibt verfolgt, auch wenn das Muster später dazukommt. Herausnehmen geht mit git rm --cached <datei> — der Inhalt bleibt dabei auf der Platte.

Ich habe Mist gebaut, aber noch nicht committet

git checkout -- datei.txt   # eine Datei zurücksetzen
git restore datei.txt       # dasselbe, neuere Schreibweise

Beides verwirft deine Änderungen an der Datei. Das ist nicht rückholbar — vorher git diff lesen.

Der letzte Commit war falsch

git reset --soft HEAD~1   # Commit weg, Änderungen bleiben bereitgestellt
git reset --hard HEAD~1   # Commit UND Änderungen weg
--hard verwirft Arbeit Es löscht die Änderungen wirklich. Und: was schon gepusht war, ist auf GitHub weiterhin da. Solche Befehle gehören nicht in einen Zweig, auf dem andere arbeiten.

Es hängt und will eine Nachricht

Öffnet sich ein Texteditor im Terminal (meist nano oder vim), will Git eine Commit-Nachricht.

In nano: Text tippen, dann Strg+O, Enter, Strg+X.
In vim: i drücken, tippen, dann Esc und :wq und Enter.

Begriffe

WortBedeutet
RepositoryDer Ordner samt seiner ganzen Historie. Kurz: Repo.
CommitEin festgehaltener Stand, mit Datum, Autor und Nachricht.
Zweig / branchEine Nebenspur der Historie. Der Hauptstand heisst main.
originDer Kurzname für die Kopie auf GitHub.
HEADDer Stand, auf dem du gerade stehst. HEAD~1 ist einer davor.
MergeZwei Zweige zusammenführen.
Pull RequestDie Bitte auf GitHub, einen Zweig in main aufzunehmen.
KonfliktBeide Seiten haben dieselbe Zeile geändert. Git fragt, welche gilt.
Wenn du nur eine Sache mitnimmst git status vor jedem Schritt. Er sagt dir, an welchem der vier Orte deine Änderung gerade liegt — und damit, welcher Befehl als nächster fehlt.
